When an agent needs authority it doesn't hold, it asks, and a person decides. Avow stores each ask as an approval request, one record of one shape, so a harness, the console and any inbox show it the same way. An agent can ask and read where its requests stand. It can never approve, decline or change one, its own or another agent's.

## What an agent can ask for

| Kind | What approving it changes | Reasons |
| --- | --- | --- |
| `agent_authority` | Puts the agent's key on the business's account under a mandate the administrator sets | `new_agent` |
| `raise_limit` | Replaces the agent's mandate with one at the higher limit per commitment or on open reserves | `over_commitment_limit`, `reserves_limit_full` |
| `name_supplier` | Names a supplier on the lock and adds it to the agent's mandate | `new_supplier` |
| `open_mode` | Sets the lock's cap on reserves held with suppliers listed in the testnet's supplier registry | `listed_suppliers` |
| `seller_mandate` | Signs a seller's mandate for the agent's signing key, with exactly the limits asked for | `new_seller`, `seller_limits` |

An agent asks for agent authority through `connect`, as it always has. Avow takes the other kinds as each ships, and refuses one it doesn't take yet with `approval_request.kind_unavailable`. None of them approves a single payment.

## Raising a limit

An agent at its limit asks with `askToRaise` on its `SandboxAgent`, or the MCP server's `request_change` tool, naming `per_commitment` or `open_reserves` and the new limit. The SDK starts the ask from the mandate the agent holds now, since Avow takes an ask only when its starting value matches. Avow refuses, with `approval_request.beyond_limits`, a raise the agent couldn't use, such as a limit per commitment above what it may hold at once or above its key's daily limit.

The administrator approves on the signing page, and the same page signs the mandate that replaces the agent's current one with only that limit raised. The console sends it to `POST /v1/sandbox/approval-requests/{requestId}/execution`. Avow records it and marks the request `active` in one step, under a lock on the agent, once the mandate names the agent's current mandate as the one it replaces and changes nothing but the limit asked for. Anything else is refused with `approval_request.change_mismatch`. The agent picks up the new mandate the next time it reads its mandates, within half a minute, and `agentRequest` or `request_status` says when the request is active.

The reason is a code from the list above, and Avow shows its own words for it. An agent writes no text into a request, so a request can't carry instructions to whoever reads it.

## Naming a supplier and opening the lock

An agent asks for a supplier with `askToNameSupplier`, or for open mode with `askToOpen`, or with the MCP server's `request_change` tool. Both change state on the business's lock, so the request records the state it was made against, and the lock itself refuses the change if that state moved.

- **A supplier.** The request records the supplier's account and how many times its place on the lock has changed. On approval the signing page sends `approveSupplierIf`, which names that count and the request's window, where the lock doesn't name the supplier yet, and then the mandate that adds the supplier to the agent's own list. The lock reverts with `StaleChange` if the business named or removed the supplier since, so a removal is never undone by an older approval. Naming a supplier on the lock lets every agent of the business whose mandate allows it commit with it, and the signing page says so.
- **Open mode.** The request records the cap and how many times it has changed. On approval the signing page sends `setOpenSupplierCapIf`, which names both, the new cap and the request's window. Every change to the cap raises the count, so a change in between is caught even when the cap went back to where it was.

Avow judges a lock change by where the lock stands. The request becomes active once the lock holds what was asked, through the transaction that carried out exactly the approved change, or because the lock already names the supplier or holds the approved cap, whoever changed it. A supplier the lock already names needs only the mandate. The request becomes stale once the lock's count moved and it holds something else, since its guarded change can then never land. So a change that landed is found active whoever reports it, the console or anyone else, while the lock still holds it. Running out of gas, a dropped transaction or a network error leaves the request approved, so the administrator can send it again within the hour. The lock refuses the change once the hour is over. For ten minutes after, Avow still marks the request active if the lock holds what was asked, by whatever route it got there.

Avow reads what a business's lock can do from the lock itself. A lock made before these guarded changes takes no open mode request, which Avow refuses with `approval_request.lock_unsupported`. Its supplier requests are carried out through the lock's signed supplier change, which names the same count. Opening the lock directly from the console's settings works on every lock.

## Asking for authority to sell

A selling agent asks for a [seller's mandate](/docs/reference/seller-mandate) with the `seller_mandate` kind. Its terms are the whole of what the mandate would let it do, which is every line of what it may sell, the most for one order, the most promised and not yet delivered, how far ahead, the lowest charges, the buyers and when a person decides. The request's agent key is the agent's signing key, the one the mandate binds. `sellerMandateTermsProblem` in `@avow-finance/spec` holds the terms to the rules a mandate's own terms meet, so an ask that could never be signed is refused when it arrives.

An agent that holds no seller's mandate asks with `new_seller`. One that holds a mandate and needs other limits asks with `seller_limits`, and names every limit again, since the request carries the whole of the new terms.

Approving signs a mandate. The request stays approved until the root key signs a `SellerMandate` for that signing key which carries exactly the terms asked for, checked with `carriesSellerMandateTerms`, and which replaces the mandate the request was made against. A mandate with one limit moved carries out nothing.

`sellerMandateWords` in `@avow-finance/sdk` gives every limit as a label and a value, in the order a person reads them, and `changeWords` builds the card's rows from it. No limit is left off, so the card shows what a signature would grant. Where a rule reads Avow's records of a buyer, the words say the country is self-declared and the business check is simulated.

The spec holds this kind and Avow doesn't take it yet. Until it does, Avow answers `approval_request.kind_unavailable`, nothing stores or enforces a seller's mandate, and a selling agent's signing key is still its only limit.

## The record

Each request carries its id, its kind, the business, the agent's key, the exact terms, the reason, when it was asked and when it expires. Beside the terms Avow stores the basis, the state the request was made against. For a raise that's the hash of the agent's current mandate. For a supplier it's that hash, the supplier's account and how many times its place on the lock has changed. For open mode it's the cap the lock held and how many times the cap has changed. For a seller's mandate it's the hash of the mandate the signing key holds, or null when it holds none.

The agent sends only the kind, the terms and the reason. Avow reads the basis itself, and refuses with `approval_request.terms_mismatch` a raise whose starting value isn't what the agent holds now, a supplier the mandate already names, and open mode at the cap the lock already holds. A supplier has to be one Avow has a profile for, or the ask is refused with `supplier.unknown`.

A change to authority waits a day for a decision. Agent authority waits an hour, as an agent's request always has, since anyone can ask and each request holds one of the business's ten waiting places. Opening a request's link never moves its expiry.

## Deciding

The business account's root key decides a request by signing an `ApprovalDecision` under the business's lock. It names the request id, the business, the agent, the hash of the kind, reason and terms, the hash of the basis, the expiry, and whether it approves or declines. A signature decides that request and no other. Signing in to the console proves who the administrator is, and never stands in for this signature.

The console's signing page is where a person does this. `approvalRequestLink` in `@avow-finance/sdk` gives the link to one request, and an agent sends it to its person. The page shows the business, the agent, the kind and the terms with old beside new, and signs with the passkey that is the account's root key. The passkey belongs to the console's domain, so a page that copies this one anywhere else can't produce a signature Avow accepts. The link grants nothing to whoever opens it. Agent authority opens the same card the console has always shown for a new agent, where the administrator approves it or declines it. A decline frees the request's waiting place at once.

`approvalDecisionTypedData` in `@avow-finance/spec` builds what the root key signs, and the decision goes to `POST /v1/sandbox/approval-requests/{requestId}/decision`.

Avow checks the signature first, then checks the basis again under a lock on the agent or the business. If what the request would change has changed since it was asked, such as the administrator cutting the limit while a raise waited, the request becomes `stale` and never applies. An approval can't overwrite a newer decision. The same decision sent again, even signed afresh, is answered with the request as it stands.

## Where a request stands

| State | Means |
| --- | --- |
| `waiting` | Nobody has decided it yet |
| `approved` | The root key signed it, and its change hasn't landed yet |
| `executing` | Its change is on its way, such as a transaction to the lock |
| `active` | Its change landed, and the agent can use it |
| `failed` | Its change didn't land, with the reason |
| `declined` | The root key declined it |
| `expired` | It lapsed before anyone decided it, or its change didn't start within an hour of approval, in which case it carries `approvedAt` |
| `stale` | What it would change changed first, so it never applies |

An agent treats what it asked for as usable only once its request is `active`. Applying a change is idempotent, so a retry never applies it twice.

## Limits on asking

A request is never a way to wear an administrator down, so Avow limits how agents ask.

- An ask identical to one already waiting is answered with that request.
- A different ask of the same kind while one waits is refused with `approval_request.already_waiting`. For suppliers, that's per supplier.
- An agent asks one business for at most ten changes a day, refused after with `approval_request.asks_exhausted`. Asking for agent authority isn't counted.
- After a decline the agent waits a day before asking the same again, refused meanwhile with `approval_request.cooling_down`.
- The business decides which changes its agents may ask for with `POST /v1/sandbox/approval-policy`, signed by its root key, and reads it back at `POST /v1/sandbox/approval-policy/current`. A business that never set one lets its agents ask for every change, and asking for agent authority is always open.

## Reading requests

The business account's root key reads every request waiting on its administrator, oldest first, with `sandboxWaitingRequests` in `@avow-finance/sdk`, or `POST /v1/sandbox/approval-requests/waiting`. The console's waiting list reads the same requests.

An agent reads its own requests at its business, signed by its key under the business's lock, at `POST /v1/sandbox/approval-requests/mine`, newest first, or one at `POST /v1/sandbox/approval-requests/{requestId}`.
