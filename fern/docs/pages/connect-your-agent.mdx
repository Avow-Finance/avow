Your agent keeps its own key, on the machine where it runs. Your business's administrator approves it once in the console with a passkey, and from then on it commits within the limits that approval set. Avow never holds the agent's key or the administrator's.

That's what lets agents do business with agents they've never met. A counterparty checks each commitment against the business that stands behind it and the money reserved for it, and needs no prior relationship with your agent.

## Before you start

- A passkey on the device where you'll approve. If you don't have a sandbox business yet, the agent's link sets one up for you.
- Node 22.12 or later in your agent's project, for the terminal and every client but Claude Desktop's extension.

## Let your agent connect itself

An agent in any MCP client can ask for its own authority through Avow's MCP server. Run the line for your client in your agent's folder, since the client starts the server against that folder's agent and a second agent needs a folder of its own.

| Where your agent runs | Run in your agent's folder |
| --- | --- |
| Claude Code | `npx avow-sandbox mcp add claude-code` |
| Claude Desktop | Install the extension below, or run `npx avow-sandbox mcp add claude-desktop` |
| Cursor | `npx avow-sandbox mcp add cursor`, which adds the server to the folder's `.cursor/mcp.json` |
| VS Code with Copilot | `npx avow-sandbox mcp add vscode`, which adds it through `code --add-mcp` |
| Codex | `npx avow-sandbox mcp add codex`, which adds it through `codex mcp add` |
| Any other MCP client | `npx avow-sandbox mcp add config` prints the `mcpServers` block to paste into its settings |

A client whose own command isn't on your path gets the exact line to run instead. A settings file that isn't valid JSON is left as it is, and the command prints what to add.

In Claude Desktop, install the extension. Download [avow-sandbox.mcpb](https://github.com/Avow-Finance/avow/releases/latest/download/avow-sandbox.mcpb) and double-click it, or drag it onto the Claude Desktop window. It then shows as a Desktop connector under Customize > Connectors. The agent keeps its key in an `avow-agent` folder in your home folder, which Claude Desktop sets for you. Change it in the connector's settings only to run a second agent, which needs a folder of its own. Nothing else needs installing, because Claude Desktop runs the extension with its own Node.

Then ask the agent to connect:

```
Connect to Avow as "Research agent".
```

It calls the `connect` tool, which makes the agent's key, keeps it in `.avow` in that folder and asks for authority. The agent hands you a pairing code and a link. Clients that show MCP Apps, Claude Desktop among them, also show a card with the code and a button that opens the link, and the card changes to approved once you approve. Every client gets the code and link as text, so nothing depends on the card. Open the link on your phone, sign in with your business's passkey or set up a business, check the console shows the same code, set the limits and approve. Your approval binds the request to your business. The link names the request and nothing more, so whoever opens it still needs a business's passkey to approve anything.

If you'd rather the agent asks one business only, give it the business ID from the console's settings, which open from your business's name, such as `Connect to my Avow business sandbox-9df2eec2a472a1819d20fba1f8a6f70a232f6447 as "Research agent"`.

The server waits in the background while you approve, and the agent's `status` tool says when it's connected. The console shows which client the agent says it runs in, such as the MCP client that started it or the terminal. The agent reports that itself, so treat it as a label. From then on `authority`, `check`, `book` and `commitments` act within the limits you signed, and `verify` checks a commitment another agent shared, before or after connecting. `check` says whether a booking would pass right now, and which layer would refuse it if not, without booking anything or moving money. If Claude restarts before you approve, asking the agent to connect again picks up the same request with the same code.

## Connect from the terminal

In your agent's project folder:

```sh
npx avow-sandbox connect --name "Research agent"
```

The name is what the administrator reads on the card they approve, so it holds 1 to 60 UTF-16 code units on one line in any script, with most emoji counting as two, and a name with a double quote, two apostrophes or backticks side by side, emoji joined by a zero-width joiner, or a hidden character or mark that changes which way text reads is refused before anything is sent. A wide space from a Japanese, Chinese or Korean input method counts as a plain space.

It makes the agent's key, keeps it in `.avow` in that folder, and asks for authority. Whoever opens its link signs in or sets up a business and approves, and that binds it to their business. Add `--business <id>` to ask one business only. It prints a pairing code and a link to the request, with a QR code for your phone when you're at the terminal:

```
  Pairing code  7K3Q-M9XD

  https://testnet.avow.finance/#approve-0x…
```

Open the link, or find the request under Agents in the console, and check it shows the same code. Anyone can send a request, so the code is how you know this one came from your terminal. Set the agent's limits and approve. Your device asks for the passkey once, for one transaction that puts the agent's key on your account with its limits and approves its supplier. That transaction carries the mandate's hash as the key's witness, so it's your account's word on exactly the mandate the card showed, and changing any term of the mandate breaks the match. The agent has no authority until the transaction succeeds.

The command waits while you approve, then enrolls the agent with Avow and exits. Stop it at any time and run it again, and it asks with the same key and the same code.

## See the whole loop

With the agent connected, one command books twice with Avow's demo GPU supplier, a test business, keeps one booking and cancels the other late, in about ten minutes.

```sh
npx avow-sandbox loop
```

The kept booking's \$10 reserve comes back whole at its release date. The late cancellation costs your business \$5 of its test dollars, the charge its terms allow, which Avow confirms from its own record of when your agent cancelled. The run needs a mandate that names the demo supplier and permits cancelling, and it says so before booking anything when yours doesn't. [Run all four in an hour](/docs/walkthroughs/overview) sets out each step.

## Connect from your own code

```ts
import { connectToBusiness } from '@avow-finance/sdk'

// In Node the key and mandate go in .avow in the working directory.
const agent = await connectToBusiness({
  businessId: 'sandbox-9df2eec2a472a1819d20fba1f8a6f70a232f6447',
  label: 'Research agent',
  onEvent: (event) => {
    if (event.type === 'asked') console.log(`Pairing code ${event.pairingCode}`)
  },
})
```

Once it's connected, `sandboxAgent()` and the MCP server both read the same folder, so the agent books through either with the key and limits you approved.

## Do business with another business's agent

Two businesses connect an agent each. The seller's agent connects with `--sell`, which makes it a signing key of its own to quote and accept with. The seller's administrator approves it with one more passkey touch, which registers that key for the business.

```bash
# The seller's folder. Leave listen running, since nothing wakes it when it stops.
npx avow-sandbox connect --business <seller-id> --name "Fine-tuning agent" --sell
npx avow-sandbox listen

# The buyer's folder, approved for jobs from the seller's business.
npx avow-sandbox connect --business <buyer-id> --name "Research agent"
npx avow-sandbox order --supplier <seller-id>
```

An order goes through four steps, and nothing is reserved until the third.

1. The buyer's agent sends a request that lapses at a time it names, ten minutes by default.
2. The seller's agent books the compute the job needs and returns signed terms that rely on that booking.
3. The buyer's agent checks the terms, its own authority and the booking on chain, then funds the commitment from its business's lock.
4. The seller's agent accepts under the lock's rules.

A request nobody answers lapses with nothing reserved. A seller that goes quiet after the buyer funded leaves a funded commitment awaiting acceptance, and the lock returns the reserve once its acceptance deadline passes. Both consoles show where each order stands.

Avow keeps every order until it ends, and reading the inbox never removes one. An agent that crashes reads the same orders when it starts again, and each step it repeats is answered the same, so a retry never makes a second commitment or a second payment. The seller's agent keeps its compute booking in `.avow` before it quotes, so a restart quotes with that booking and books nothing new. The buyer's agent keeps its order there before sending it, and `order` picks up an unfinished order to the same business before it sends another, funding nothing the lock already holds.

The same flow runs from code with `sandboxMailbox()`, whose `buy`, `inbox`, `sell` and `listen` take the steps above.

## Check a commitment someone shared

Every commitment has a link anyone can open to check it, and an agent that books shares that link. An agent on the other side, connected to Avow or not, checks it with one call before relying on it. The MCP server's `verify` tool and the terminal's `verify` command do the same check.

```bash
npx avow-sandbox verify "<link>" --payee <your payout address>
```

The check reads the lock on Tempo through the factories the SDK trusts and never asks Avow, so it needs no key, no business and no connection. It passes when one of Avow's factories created the lock and the lock holds that commitment under the link's terms hash. Then it says how much the lock holds, whether the commitment waits for the supplier's acceptance, stands, has a charge open or has ended, which account it pays, and when free cancellation ends and the reserve releases. With `--payee`, or `payee` in the tool, it says whether the commitment pays you, and the command exits with 1 when it doesn't or when the chain doesn't back the commitment.

The link carries the terms hash, and the terms themselves come from the buyer. Matching them to that hash is what ties them to the reserve, and `verifyCommitmentTerms` in `@avow-finance/verifier` does that for anyone holding them.

## Teach your agent when to commit

The repo's `skills/avow-commitments` folder is an Agent Skill. It tells an agent when a commitment is the right tool and when a payment is, how to connect and stay inside its limits, and how to check a commitment someone sent it. Copy the folder into your agent's skills, such as `~/.claude/skills` for Claude Code, and the agent loads it when a task calls for a commitment.

## What the approval holds the agent to

- **The mandate** names the suppliers the agent may commit with, the most it may reserve for one commitment and in total, and when its authority ends. Avow refuses a reserve outside it.
- **The key's limits** sit in your account's keychain on Tempo. The chain refuses a transaction over the daily limit or outside the lock, whatever the agent's code does.
- **The lock** reserves only for suppliers your administrator approved on it.

Revoking the agent in the console removes its key from your account. Its next transaction fails on chain, and what it already reserved stays in your lock until those commitments end.

## On testnet

Requests lapse after an hour unanswered. The agent's key sits in a plain file in `.avow`, readable by anything on that machine that can read the folder. An agent that also has a shell or file tools can reach it, so keep the folder out of the agent's reach if that matters to you. Nothing here moves real money.
