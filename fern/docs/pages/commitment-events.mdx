A commitment event is the notice of one change in a commitment's life, such as a reserve reaching the lock, the supplier's acceptance or a charge leaving the reserve. It is one typed record with a code and that code's fixed fields, so your code can act on a change without parsing a sentence.

`@avow-finance/spec` holds the shape, its JSON form, its slot and its hash. An agent reads a commitment's events straight from its lock with the SDK or the MCP server's `commitment_events` tool. Avow can also post a business's events to an address it adds, signed with a key Avow publishes, though that isn't switched on for testnet yet. The supplier's adapter sends its webhook events in this shape too.

## An event is a notice

The lock is the record. An event tells you something changed and where to look, and that is all it does.

- **It grants nothing.** No event gives an agent authority, approves a request or moves money.
- **It proves nothing by itself.** An event carries no signature. `commitmentEventProblem` says an event is well formed and says nothing about whether it is true, so anyone can write a well-formed event about any commitment. Before you act on one, read the lock with the verifier, or check the signed message the event names.
- **It carries no words.** Every string in an event is hex of a fixed length or a word from a fixed list. Every other value is a whole number, a decimal string of one in JSON, a flag or null. No field holds text a person or a model wrote, so an event can't carry an instruction to whoever reads it. A test in the spec walks every field of every code and fails if one could hold anything else.
- **It names no business.** An event names the commitment by its chain, its lock and its id. Each side of a commitment already knows the other, so no event carries a business id, a party's account or a payout address. The lock's address is the one thing in an event that belongs to a party. It names the terms by their hash and never carries them, since terms hold words a party wrote.

## What every event carries

| Field | Type | Value |
| --- | --- | --- |
| `schemaVersion` | string | `"1"`, which is `COMMITMENT_EVENT_VERSION` |
| `code` | string | One of the codes below |
| `commitment` | object | `chainId`, `lock` and `commitmentId`, with hex in lower case |
| `source` | string | Who states the event, which says how its time is known |
| `at` | Unix seconds | When the change happened, by that source's clock |

Every code but `reserve.owed_paid` also carries `termsHash`, the hash of the terms the commitment was made under. An event names no side, since a lock reserves the buyer's side only.

In JSON an amount is a decimal string, a time is a decimal string of unix seconds, and hex is in lower case.

An amount's unit depends on who states it. A `block` event's amounts are in base units of the lock's token, exactly as the lock logged them, since no log names the token or its decimals and an event is written from the logs alone. A lock's token is fixed when the lock is made, so read it once from the lock's `token()` and its decimals from the token. Avow's and a supplier's amounts are in micros of the terms' currency. On testnet the token has six decimals, so the two read the same, and an event never relies on that.

## Who states an event

Three sources can state an event, and each event says which one did. A reader never has to guess which clock a time came from.

| `source` | Who states it | What `at` is | What else the event carries |
| --- | --- | --- | --- |
| `block` | Whoever read the lock's log | The time of the block that holds the log | `blockNumber`, `transactionHash` and `logIndex`, so anyone can read the log from the chain |
| `avow` | Avow's API | Avow's clock when it recorded the change | Nothing |
| `supplier` | A supplier's adapter | The clock of the machine the adapter runs on | Nothing |

Whoever writes a `block` event writes it from a final block only, so no event names a log that a reorganization later drops. That is a rule for the writer, and nothing in an event shows it was kept. `reserve.owed_paid` leans on it hardest, since its slot takes the transaction: one owed payment logged in a dropped block can land again in another transaction, and an event written from the dropped block would give that payment a second slot. A `block` event with a made-up place passes the check like any other, so read the log it names before you rely on it.

A supplier's statement is the supplier's own word. It is good for the supplier's own system and no more, and nobody else should act on it.

The code fixes which sources can state it. A reserve the lock took is stated from a block and never from a clock. In TypeScript, checking an event's `code` and `source` narrows it to exactly the fields it carries.

## The codes

`booking` codes are changes off the lock, to the agreement and to what Avow records beside it. `reserve` codes follow the money the business reserved. `charge` codes follow a charge the supplier reported, through to its payment or its ruling. The table lists them in the order a commitment's life can reach them.

| Code | Stated by | When | Carries |
| --- | --- | --- | --- |
| `booking.agreed` | `avow`, `supplier` | Both sides signed the terms agreement. Nothing is reserved yet | `termsHash`, `reserve`, `agreementExpiry` |
| `reserve.approved` | `avow` | Avow's reserve check passed and Avow signed its approval | `termsHash`, `reserve`, `approvalHash`, `approvalExpiry` |
| `reserve.locked` | `block` | The lock took the reserve | `termsHash`, `reserve`, `approvalHash`, `mandateHash` |
| `reserve.held` | `supplier` | The supplier's own check of the funded reserve passed, so it holds the capacity without granting it yet | `termsHash`, `reserve`, `agreementExpiry` |
| `reserve.accepted` | `block`, `supplier` | The lock took the supplier's acceptance, which is when the commitment exists | `termsHash`, `acceptanceHash`, `reserve`, `agreementExpiry`, `acceptedIn` |
| `booking.lapsed` | `avow`, `supplier` | The booking ended with no acceptance by its deadline | `termsHash`, `reserve`, `agreementExpiry` |
| `booking.start_requested` | `avow` | Avow timestamped the business's signed request to start | `termsHash`, `requestHash` |
| `booking.started` | `avow` | Avow recorded the supplier's signed start receipt | `termsHash`, `requestHash`, `receiptHash`, `startedAt` |
| `booking.cancelled_late` | `avow` | Avow recorded the business's cancellation after free cancellation had ended | `termsHash`, `requestHash` |
| `charge.reported` | `block` | The lock took the supplier's report of a charge. Nothing has moved | `termsHash`, `reportNumber`, `kind`, `kindCode`, `amount`, `evidenceHash`, `answerBy`, `contested` |
| `charge.withdrawn` | `block` | The supplier withdrew its report before Avow answered it | `termsHash`, `reportNumber`, `evidenceHash` |
| `charge.confirmed` | `block` | Avow confirmed the report, and the lock sent the reserve above the charge back to the business | `termsHash`, `reportNumber`, `amount`, `evidenceHash`, `returned` |
| `charge.referred` | `block` | Avow sent the report to a ruling | `termsHash`, `reportNumber`, `evidenceHash`, `returned` |
| `charge.unanswered` | `block` | Avow didn't answer the report by its deadline, so it waits for a ruling | `termsHash`, `pausedAt`, `evidenceHash`, `returned` |
| `charge.paused` | `block` | Avow paused a charge it had confirmed | `termsHash`, `pausedAt`, `evidenceHash` |
| `charge.contested` | `block` | The business contested the charge, and nothing pays until someone rules | `termsHash`, `reason`, `reasonCode`, `statementHash`, `pausedAt`, `returned` |
| `charge.evidence_filed` | `block` | One party filed a piece of evidence on a paused charge | `termsHash`, `filer`, `number`, `evidenceHash` |
| `charge.ruled` | `block` | A ruling was posted. Nothing has moved, and the lock sends its amounts once the ruling delay has passed | `termsHash`, `ruledBy`, `toSupplier`, `evidenceHash` |
| `charge.charged` | `block` | The contest window closed with no contest, so the lock took the charge out of the reserve and sent it to the supplier | `termsHash`, `amount`, `evidenceHash` |
| `charge.resolved` | `block` | The lock settled a paused charge, by its ruling or by the day-90 default | `termsHash`, `byRuling`, `toSupplier`, `toBusiness`, `evidenceHash` |
| `reserve.released` | `block` | The lock sent what it still held back to the business | `termsHash`, `cause`, `reason`, `reasonCode`, `evidenceHash`, `returned` |
| `reserve.owed_paid` | `block` | The lock paid an amount it had recorded as owed | `party`, `amount` |

`reserve.accepted` carries `acceptanceHash` when a block states it, and `reserve`, `agreementExpiry` and `acceptedIn` when a supplier's adapter does. `acceptedIn` is the acceptance's transaction, or null when the adapter found the acceptance on the lock and never saw the transaction.

`booking.lapsed` says the booking ended unaccepted. It doesn't say whether a reserve had come. A booking lapses with no reserve when the agent never funds one. It also lapses with a reserve on the lock when the acceptance never lands by the deadline, and that reserve is still locked when the event is stated. It then goes back to the business, which is a `reserve.released` with the cause `not_accepted` or `returned_by_avow`.

A few fields need a word.

- **`reserve`** is the most the supplier can charge on the commitment. The events about the agreement and the reserve carry it. Later events from a block leave it out, since the lock's later logs don't hold it.
- **`reportNumber`** is 1 or 2, since a lock takes at most two reports for a commitment. The lock's logs for a pause and for a payment carry no report number, so those events carry none.
- **`kind`** is `lateCancellation` or `noShow`, and `kindCode` is the number the lock logged. `kind` is null for a number this spec has no name for.
- **`reason`** on a contest is one of the six reasons a business [contests a charge](/docs/charges-and-disputes/contesting) for, and `reasonCode` is the number the lock logged. A lock takes any number from 0 to 65,535 there, so `reason` is null for one that names none.
- **`contested`** on a report says the business's contest of an earlier report stands, so the new report waits for a ruling from the start.
- **`pausedAt`** is the moment the days to a ruling count from, which can be earlier than `at`.
- **`evidenceHash`** on a report is the hash the supplier's signed report carried, and the lock logs it again when the report is withdrawn, confirmed, unanswered, charged or resolved. On a referral, a pause and a ruling it is the hash Avow or the ruler gave with that step, and on a release the hash a supplier's consent carried, or 32 zero bytes.
- **`ruledBy`** is the address that posted the ruling, which is Avow's ruling key or the arbiter the terms name. It is the arbiter when it matches the arbiter in the terms.
- **`byRuling`** on a resolution is true when the lock followed a ruling and false for the day-90 default.
- **`filer`** and **`party`** are `business` or `supplier`. The business is the one that reserved.
- **`startedAt`** is the start the supplier's receipt states, by the supplier's word.

A release says which of the lock's five steps made it and what reason that step gave.

| `cause` | The step | `reasonCode` and `reason` |
| --- | --- | --- |
| `returned_by_avow` | Avow returned a reserve the supplier hadn't accepted | Any number from 0 to 255, as Avow gave it. 1 means the business revoked the agent that made the reserve, which `avowReturnReasonOf` reads as `agentRevoked`. `reason` stays null, since an event names only a consent's reasons |
| `cancelled_in_time` | The business took its reserve back before free cancellation ended | 0 and null |
| `supplier_consent` | The supplier's account consented to give the reserve back | Any number from 0 to 255. `reason` is `kept` for 1 and `supplierFailed` for 2, and null for any other |
| `not_accepted` | A reserve nobody accepted went back at the acceptance deadline | 0 and null |
| `reached_release_date` | A reserve with nothing reported went back at its release date | 0 and null |

Avow doesn't return reserves for a revoked agent yet, so no lock has logged that reason. Until it does, a revoked agent's unaccepted reserve goes back at its acceptance deadline as `not_accepted`.

A business cancelling in time has no code of its own. It takes its reserve back on the lock, so it is a `reserve.released` with the cause `cancelled_in_time`. `booking.cancelled_late` is the cancellation Avow records once free cancellation has ended, which a late-cancellation charge rests on.

## Money a lock sends

Several of a lock's steps send money, and a transfer can fail, for a paused token or a blocked address. When one does, the step still stands and the lock records the amount as owed to that party. Anyone can have the lock pay it later. An event tells the two apart, so no event says money arrived when it didn't.

Each amount a lock sends is an object with the amount and what became of it.

```json
{ "amount": "150000000", "state": "owed" }
```

`state` is `paid` when the transfer went through in that step, and `owed` when it failed and the lock recorded the amount as owed. A step that sends nothing carries null in the amount's place, so an amount of zero never has a state. `sentStates` in the spec reads which from the step's receipt, as [Written from the lock](#written-from-the-lock) sets out.

| Code | Amounts the lock sends | To |
| --- | --- | --- |
| `charge.confirmed`, `charge.referred`, `charge.unanswered`, `charge.contested` | `returned`, the reserve above the charge, or null when there is none or the report isn't final yet | The business |
| `charge.charged` | `amount`, the charge | The supplier |
| `charge.resolved` | `toSupplier` and `toBusiness`, either of which can be null | Each party |
| `reserve.released` | `returned`, everything the lock still held | The business |

`reserve.owed_paid` is the lock's later payment of an owed amount to the `party` it was owed to. The lock adds up what it owes one party on a commitment and pays the sum, so one `reserve.owed_paid` can settle several `owed` amounts. `toSupplier` on `charge.ruled` is a plain amount, since a ruling moves nothing when it is posted.

An `owed` amount has left the commitment's reserve all the same. A `reserve.released` with an `owed` amount means the lock holds nothing more for the commitment and owes the business that amount.

## What settles a step

Every code names what a receiver checks when two statements of it differ and neither source outranks the other. `COMMITMENT_EVENT_CHECKED_BY` lists them, from the five in `COMMITMENT_EVENT_CHECKS`.

| Check | What the receiver checks |
| --- | --- |
| `lock` | The lock's state and its logs, read with the verifier |
| `terms_agreement` | The terms agreement, with both signatures: the buyer's agent key and the supplier's signing key |
| `approval` | Avow's approval of the reserve, signed by Avow's approval key, which `approvalHash` names |
| `timestamped_request` | The business's signed request, with Avow's signed timestamp over its digest, which `requestHash` names |
| `start_receipt` | The supplier's signed start receipt, which `receiptHash` names |

| Code | Settled by |
| --- | --- |
| `booking.agreed`, `reserve.held` | `terms_agreement` |
| `reserve.approved` | `approval` |
| `booking.start_requested`, `booking.cancelled_late` | `timestamped_request` |
| `booking.started` | `start_receipt` |
| `reserve.accepted`, `booking.lapsed` | `lock`, then `terms_agreement` for the reserve and the agreement's expiry |
| Every code stated from a block | `lock` |

Each signed message can be hashed and its signature checked by whoever holds it, without asking anyone. `reserve.locked` also names the mandate the business's administrator signed for the agent by `mandateHash`, and a block's `reserve.accepted` names the supplier's signed acceptance by `acceptanceHash`. An `evidenceHash` or a `statementHash` is the hash of a document. It lets you match a document you hold, and it is no signature.

## The slot and the hashes

An event has three derived values, and each answers its own question. None travels in the event. `commitmentEventSlot`, `commitmentEventStatementHash` and `commitmentEventHash` compute them, and each throws on an event that isn't well formed.

The slot says which step of which commitment an event is about.

```
keccak256(abi.encode(string "avow:commitment-event-slot:v1", string canonicalJson))
```

The canonical JSON, RFC 8785 as the terms use, is an object with the `code`, the `commitment` and a `key` object that holds the code's key fields. `COMMITMENT_EVENT_KEYS` lists each code's key fields.

| Codes | Key fields | So |
| --- | --- | --- |
| `reserve.approved` | `approvalHash` | Avow can approve a commitment more than once, and each approval has its own slot |
| `booking.start_requested`, `booking.cancelled_late` | `requestHash` | Each signed request has its own slot |
| `booking.started` | `receiptHash` | Two receipts for one start request have two slots |
| `charge.reported`, `charge.withdrawn` | `reportNumber` | Each of a commitment's two reports has its own slot |
| `charge.evidence_filed` | `filer`, `number` | Each piece of evidence has its own slot |
| `reserve.owed_paid` | `party`, `transactionHash`, `logIndex` | A lock numbers no such payment, so each is told apart by where its log sits, which is why its writer waits for a final block |
| Every other code | None | The step happens at most once for a commitment |

The terms hash is no part of a slot, and neither is the source, the time or anything the event says happened. Two events in one slot can say different things. One can report $250 for a late cancellation and another $5 for a no-show, both as report 1.

The statement hash names what a source said, whenever it said it.

```
keccak256(abi.encode(string "avow:commitment-event-statement:v1", string canonicalJson))
```

Its canonical JSON is the whole event without `at`, with nothing else left out. A supplier's adapter that records one step again after a restart, with a later time, makes the same statement. Use it to tell a step recorded twice from two statements that disagree.

The event hash names one event, whole.

```
keccak256(abi.encode(string "avow:commitment-event:v1", string canonicalJson))
```

It covers every field, the source and the time among them. Two deliveries of the same event have the same hash, and two events that differ in anything have two. Use it to drop exact redeliveries.

## The receiver's rules

`sameSlot(held, arrived)` applies these rules to two events of one slot and returns what to do.

1. **Drop a repeat, and only a repeat.** An event with the same event hash is the same event delivered again. Two statements from Avow's clock, or two from one supplier's, with the same statement hash are one step recorded twice, so drop the later and keep the earlier time. Never drop an event because its slot is one you've seen.
2. **On a step the lock logs, a block's statement replaces a clock's.** That arises only for `reserve.accepted`, the one code both a block and a clock state.
3. **Avow's clock and a supplier's outrank neither each other.** When they say the same thing they agree. When they differ, check what settles the step. For `booking.agreed` that is the terms agreement with both signatures.
4. **Any other difference goes to what settles the step.** Two `block` statements that differ at all, their time included, go to the lock, since one of them names a log that isn't there. Two statements from one clock that differ in more than their time go to the lock or the signed message the code names.
5. **A slot is never proof.** A slot says which step an event is about and nothing about what happened. The stronger of two notices is still a notice.

| `sameSlot` returns | Meaning |
| --- | --- |
| `other_slot` | The two are about different steps |
| `repeat` | The one that arrived says nothing new. Drop it |
| `earlier_repeat` | The same statement from the same clock, recorded earlier. Keep the one that arrived in place of the one you hold |
| `agree` | Avow and a supplier state the same thing. Keep the one you hold |
| `arrived_replaces` | They differ, and the one that arrived is the lock's log of the step |
| `held_stands` | They differ, and the one you hold is the lock's log of the step |
| `read_the_lock` | They differ, neither outranks the other, and the lock settles the step |
| `check_signed_message` | They differ, neither outranks the other, and the signed message the code names settles it |

## Written from the lock

A `block` event is written from three things: the arguments of the step's own log, the `PaymentOwed` logs of the same receipt as `sentStates` reads them, and the time of the block. Anyone with the chain can write one and anyone can check one. `LOCK_LOGS` in the spec lists every log's arguments, and `COMMITMENT_EVENT_LOGS` names the argument each field is read from.

| Code | The lock's log | Notes |
| --- | --- | --- |
| `reserve.locked` | `Reserved` | `reserve` is the log's `amount` |
| `reserve.accepted` | `Accepted` | |
| `charge.reported` | `Reported` | `answerBy` is the log's `deadline` |
| `charge.withdrawn` | `ReportWithdrawn` | |
| `charge.confirmed` | `ChargeConfirmed` | |
| `charge.referred` | `Referred` | |
| `charge.unanswered` | `Paused` | With the cause `timeout` |
| `charge.paused` | `Paused` | With the cause `avowPause` |
| `charge.contested` | `Paused` | With the cause `contest`. `statementHash` is the log's `evidenceHash` |
| `charge.evidence_filed` | `EvidenceFiled` | |
| `charge.ruled` | `RulingPosted` | `ruledBy` is the log's `by` |
| `charge.charged` | `Charged` | |
| `charge.resolved` | `Resolved` | |
| `reserve.released` | `Released` | |
| `reserve.owed_paid` | `OwedWithdrawn` | |

An event takes four things from around its log. The chain and the lock's address are where the log was read. The commitment id is the log's `commitmentId`. The block's number, the transaction and the log's index are the log's place, and `at` is the time of that block.

`lockReceiptEvents` in the spec writes them. It takes one transaction's receipt and where it was read, which is the chain, the lock, the block, the block's time and the transaction. It gives an event for each of that lock's steps in the order of their logs, and the index of every one of the lock's commitment logs that no event accounts for. That is a log with one of the lock's signatures that doesn't decode, a step it can't state, such as a pause with a cause the spec doesn't know, and a `PaymentOwed` no step folds in, whose step then reads as paid. It reads only the lock it's given, since any contract can write a log of the same shape. Pass it only a receipt from a final block.

A log carries numbers where an event carries words. The spec holds each table and its lookup, which are `chargeKindOf`, `contestReasonOf`, `releaseCauseOf`, `releaseReasonOf`, `avowReturnReasonOf`, `pauseCauseOf` and `lockPartyOf`. A lookup gives null for a number its table doesn't list, and the event keeps the number beside the null. A consent and Avow both number their reasons from 1, so read a release's `reasonCode` with `releaseReasonFor`, which takes the cause too and never reads one table's number with the other's words. A release's `cause` has no number beside it in the event, so a `Released` log with a cause the table doesn't list makes no event, and `lockReceiptEvents` names it as unread.

`paid` and `owed` come from the lock's `PaymentOwed` log, which the lock writes inside a step, before the step's own log, for each transfer that fails. A resolution pays the supplier and then the business, so when both transfers fail its receipt holds two `PaymentOwed` logs in a row before `Resolved`. `sentStates(receiptLogs, logIndex)` reads them. For each party, it is `owed` when a `PaymentOwed` for that party, commitment and side sits between the step's own log and the lock's log before it that isn't a `PaymentOwed`, and `paid` otherwise. Logs from other contracts in between, such as the token's transfer, count for nothing. `PaymentOwed` has no code of its own.

## Order

Events carry no sequence number. No one party observes every change. The lock sees what reaches it, Avow sees what its API records, and a supplier's adapter sees its own bookings. A counter would belong to one writer, and the same step would take a different number from each.

You can rely on three things instead.

- **Changes one lock logged have the lock's own order.** `lockOrder` compares two `block` events of the same lock by block number and then by log index. For two events of different locks or chains it answers that they can't be compared, and gives no number.
- **A time compares only with times from the same source.** Avow's clock, a supplier's clock and the chain's clock are three clocks.
- **Where a commitment stands is on the lock.** An event can arrive late, twice, out of order or never. Read the lock for the state, and treat an event as the reason to look.

## Versions and new codes

`schemaVersion` changes only when a code that exists changes, in what it means or in the fields it carries, or when the slot or the hash is derived another way. A new code takes no new version.

A reader follows two rules, in this order.

1. An event of a version it doesn't read is refused as `message.schema_unknown`, before the reader looks at anything else in it.
2. An event of its own version with a code it doesn't know is refused as `event.code_unknown`, whatever else it holds. That is one event set aside. The reader keeps reading the rest, and an older reader keeps working when a code is added.

Anything else that doesn't fit is `message.invalid`, which includes a source or a field the reader doesn't know on a code it does, and a `code` that isn't written as a subject, a dot and a word.

## Reading events from the lock

An agent reads what its business's lock logged for one of its commitments from the chain, with no call to Avow. The MCP server's `commitment_events` tool does it for a commitment `commitments` lists, and so does `sandboxCommitmentEvents(commitmentId)` in `@avow-finance/sdk`. Underneath, `readLockEvents` in `@avow-finance/verifier` asks a node for the lock's logs that name the commitment, reads each transaction's receipt with `lockReceiptEvents`, and gives the events oldest first.

- **It reads the lock and nothing else.** Every event it gives is a `block` event the lock logged. Avow's own records, such as its approval of a reserve, never appear, since no lock logs them. The SDK reaches the chain through Moderato's public RPC and the factories it ships with, and reads only a lock one of them made, so nothing Avow serves, its deployment file included, decides what it reads.
- **It reads final blocks only.** It stops at the node's latest final block, so no event names a log a reorganization drops.
- **A read is bounded.** One read makes at most 10 log queries of 10,000 blocks each, so a long-lived lock never meets an endpoint's limits. When a read stops short of the final block it gives `next`, the block to carry on from. Without a starting block, the SDK starts a little before the time it recorded the commitment.
- **It names what it can't state.** A log of the commitment that makes no event comes back in `unread`, so you know the lock logged a step the SDK doesn't write.

What the read gives is still a notice. It's only as true as the lock it read is the one you think it is, so check the commitment with `verify` before you act on an event.

## Receiving events from Avow

Event delivery is off until Avow switches it on, and it isn't on testnet yet. Once it is, a business's administrator adds an address in the console and signs the add with the business's passkey. No agent can add one. Avow sends the address a challenge, and starts posting events once the address answers it, from blocks no older than that answer.

The administrator chooses what each address receives.

| Choice | What Avow posts there |
| --- | --- |
| As a buyer | Each event the business's own lock logs, for the commitments it buys |
| As a supplier | Each event of a commitment Avow recorded with the business as its supplier, which another business's lock logs |
| Both | Both of those |

Signing an address approves no transaction. A supplier address gets no event of a commitment its business doesn't supply. An address that takes both tells the sides apart by comparing the event's `commitment.lock` with the business's own lock address, both in lower case. When they match, the business is buying, and any other lock means it's supplying.

An address added before this choice existed gets the buyer's events only.

The choice is part of what the passkey signs, so it can't be changed in place. To change what an address receives, remove it and add it again with the new choice, and it answers a fresh challenge before anything more is posted.

A delivery follows Standard Webhooks' asymmetric scheme.

| Header | What it holds |
| --- | --- |
| `webhook-id` | The event's hash, the same on every try, so a repeat is one you drop |
| `webhook-timestamp` | When this try was signed, in unix seconds |
| `webhook-signature` | `v1a,` and the Ed25519 signature over `id.timestamp.body`, in base64 |
| `avow-key-id` | Which of Avow's keys signed it. Standard Webhooks has no such header, so this one is Avow's |

The body is `{ "type": <code>, "timestamp": <the block's time>, "data": <the event> }`. Avow lists its keys at `/v1/events/keys`, each with its id and, once a newer key replaced it, its `retiredAt`. A retired key stays listed for seven days.

`eventDeliveryVerifier({ apiUrl })` in `@avow-finance/sdk` checks a delivery for you. Hand it the headers and the body exactly as they arrived. It refuses a delivery whose timestamp is more than five minutes from your clock, one whose key id names no key Avow lists after one read of the keys again, which an unknown id causes at most once every 30 seconds, one signed by a key retired more than seven days before, one whose signature doesn't verify, a repeat of an id it already took, and a signed body that isn't an event or a challenge. It caches the keys for five minutes at most. When the delivery is a challenge it gives you the answer to send back, `{ "challenge": … }` with a 2xx status.

A delivery that verifies came from Avow, and it's still a notice. It grants nothing, so read the lock before you act on it. Avow retries a failed delivery on `WEBHOOK_RETRY_SCHEDULE` from the spec, the same schedule as the supplier's adapter, and one commitment's events can still arrive late or out of order, so order them by `blockNumber` and `logIndex`.

## Reading, checking and hashing

| Function | What it does |
| --- | --- |
| `commitmentEvent` | Makes an event from what a writer states, at this version. It throws on a statement the check refuses, so a writer never holds an event a reader would turn away |
| `commitmentEventProblem` | Checks an event you hold. It never throws, and an event that passes has one canonical form |
| `parseCommitmentEvent` | Reads an event from JSON, by the two rules above. It never throws |
| `commitmentEventSlot` | Gives the slot, the step of the commitment an event is about |
| `commitmentEventStatementHash` | Hashes what a source said, the event without its time |
| `commitmentEventHash` | Hashes an event whole, its source and time included |
| `sameSlot` | Applies the receiver's rules to two events |
| `lockOrder` | Orders two changes one lock logged |
| `sentStates` | Reads from a step's receipt whether the lock paid each party or recorded it as owed |
| `commitmentEventFields` | Names the fields a code carries when a source states it |

## What isn't an event

- **A refusal.** Avow refusing a reserve, or a supplier declining an order, changes nothing in a commitment's life. The caller hears it in the answer to its own request, with a reason code.
- **A failed transfer by itself.** The lock's `PaymentOwed` log has no code. The step it happened in says `owed` on the amount.
- **A change to a lock's settings.** A lock also logs a supplier being approved or removed, its cap for listed suppliers being set and an approval being cancelled. Those belong to the business's lock and to no commitment.
- **Who the parties are.** The lock's `Reserved` log holds the supplier's account, the payout address and the key that funded the reserve, and its `OwedWithdrawn` log holds the address it paid. Events leave them out, with the approval's nonce.
- **A payment of the price.** A [job's price](/docs/composable-commitments/jobs) arrives as a separate transfer, which a payment reference names and anyone checks on the chain. The reserve doesn't secure it.
- **A job's session event.** A sandbox session's `job_` events are what a developer's own process posts for its screen to show. They stay as they are, and nothing here replaces them.
- **A change to an agent's authority.** A mandate, a limit or a revocation belongs to the agent and the business, and an [approval request](/docs/reference/approval-requests) carries it.
